# Minecraft BharatCode Companion project specification

**Status** — Draft for review, 9 November 2026. This is the project-level contract. The [task list](project-tasks.md) gives the delivery order, acceptance gates, and decisions that still need evidence.

## 1. Product and release boundaries

Minecraft players summon one persistent, named, player-shaped companion and direct it through addressed chat and in-game controls. It walks the site, builds with real materials and tools, explains blockers, and remembers jobs and progress. The first builder release supports single-player, private servers, and public servers, including settlements, tested templates, and original AI layouts. A settlement requires layout approval and separate approval of each building. The production release adds verified machines and storage networks. The engineering release adds commissioned farms, redstone, terraforming, logistics, and modded factories.

The pinned development target is Java 21, Minecraft 1.21.1, NeoForge 21.1.265, Gradle 8.14.2, and ModDevGradle 2.0.91. ATM10 8.5 is the first pack target. Report support per tested version, capability, and environment. Pack-wide automation remains a research direction. Combat and adventure are outside the selected scope. Hidden world lookups, creative material generation, protection bypass, portable machine emulation, arbitrary generated code, and automatic undo are excluded. ## 3. Functional contracts

| ID | Contract |
| --- | --- |
| R1 Identity and movement | The overworld schema-v2 SavedData record owns owner UUID, companion UUID, name, active/dormant state, dimension, and last position. The live entity is a transient `noSave` projection. Keep duplicate and stale-copy fences and preserve readable unknown/corrupt data. Active cross-dimension recall refuses. Dismiss and summon can move the same identity to another dimension. Movement adds owner-controlled follow, stay, and home, bounded recovery, and safe same-dimension recall. Preserve the correct restoration chunk when the companion moves. Dismissal, logout, spectator mode, and invalid authority suspend movement. Invulnerability remains, with administrative removal supported. |
| R2 Ownership and protection | The server derives actor identity from the connection. Only the owner or an explicitly delegated actor may give permitted orders. Server policy, assigned work zones, claims, and target-specific trust apply at execution time. Check before each edit or protected interaction and again after a pause or revocation. An unknown protection state blocks world edits, external transfers, placed stations, and trip progress. Planning, chat, previews, authorized viewing, and approved internal crafting/smelting from held items remain available subject to lifecycle gates. |
| R3 Jobs and approvals | Persist ordered jobs, revisions, approvals, completed steps, wait reasons, and dependencies. Support reorder, pause, resume, cancel, and queue-or-switch. Bind an approval to the exact design/transform, zone, relevant site baseline, allowed removals, resource budget, and approval authority. Own recorded changes advance expected site state. Unexpected changes pause affected work for review. Revision, movement or rotation of the blueprint, substitutions, and expanded scope invalidate the affected approval. Recheck live authorization on resume. |
| R4 Custody and recovery | Carrying has no gameplay slot or weight cap. Page persistent storage and bound each transfer and tick. Track real item identity, data components, counts, and location. Separate reservation, extraction, held custody, consumption, handoff, output, and reconciliation. A reservation alone cannot fund an action. Refuse unsafe intake before moving items where possible. After interruption isolate ambiguous outcomes, keep confirmed balances, and pause affected dependents. Never replay an uncertain transfer or invent stock. Dismissal pauses physical jobs, crafting, and transfers. Logout pauses all companion execution and AI calls. Independent machines may keep running and must be reconciled on return. |
| R5 Building and settlements | Ask about the design, validate bounded layouts server-side, show ghosts, offer alternatives and substitutions, and obtain approval. Build safe independent steps using partial supplies already held. Acquire shortages only through already-authorized actions inside project budgets. Expose missing materials and dependent steps. Show removals separately and require explicit approval before breaking, with extra controls for containers, machines, and unknown blocks. Track manual item handoffs separately and verify manual placement before counting it complete. Keep unsupported ATM10 placements manual with actionable instructions. Use player-like work pace, real tools and durability, and tracked temporary scaffolding. |
| R6 Supplies and C0 production | Offer wait, player supply, or authorized gathering. Simulated trips award only configured basic resources from proven natural-source unlocks, use tool and rarity rules, and return earned partial output once on recall. Owner harvesting or companion observation must have trustworthy natural provenance. Gifts, crafting, and attestation alone never qualify. A started trip can progress while dismissed with an online owner and verified protection. Portable crafting/smelting uses registered server recipes, actual ingredients, fuel, time, remainders, and permitted station classes. An unsupported type becomes a player-run step. |
| R7 AI, chat, and memory | Handle addressed chat and right-click controls without AI for supported predefined actions. The owner's client calls BharatCode after setup disclosure. It may use an explicitly configured and verified alternative provider. Keep credentials on the owner client and send only addressed messages and relevant scoped context. Bind structured responses to a server-issued request and validate actor, expiry, revision, schema, bounds, recipes, live authorization, and replay before creating a proposal. Human approval remains a separate transition. Scoped trusted-player consent grants allowance use without granting the key. Provider errors pause work that needs a new AI decision. Approved executable work and basic controls remain available subject to server and lifecycle gates. Support named places, preferences, conversational memory controls, and local forget with truthful remote retention copy. |
| R8 In-game interface and catalog | Provide the fieldbook through right-click, a compact HUD, and milestone chat. Show owner, status, active job, queue, inventories, ghost, shortages, approval revision, manual work, and next action. Provide tested built-ins, personal saves of AI designs, admin-installed schematics with approved substitutions, and admin moderation before public sharing. Expose appearance/name/personality settings, trust, consent, privacy, and compatibility as each backed feature ships. |
| R9 Modded production | The server recipe manager is authoritative and JEI/EMI are optional displays. Expose C0 core actions, C1 recipe readers, C2 machine operation, C3 storage/autocrafting, C4 protection, and manual fallback separately. Each adapter declares versions, permissions, supported operations, health, and evidence. Validate real power, heat, fluids/gas, stress, progression, side access, and permissions where relevant. Honor live security and output evidence. Downgrade on missing APIs, unverified versions, reload, or failure. |
| R10 Engineering | Support requested renovations, decorations, repairs, normal-drop demolition, and terrain shaping in approved zones. Explain recipes/progression, inspect and diagnose nearby builds, and scout physically under distance/chunk limits. Build known functional blueprints first. Verify farm/redstone/factory output and safety through observable commissioning or report built and unverified. Compose reusable AI-proposed workflows from fixed validated actions. Bound on-site experimentation by approved impact, zone, and budget, with unknown and high-risk effects blocked. |
| R11 Operations and release | Enforce server-wide and per-owner bounds on jobs, placement rate, loads, queries, transfers, AI requests, and retained state. Provide pause/disable controls, redacted diagnostics, and a recoverable migration/backup procedure. Document exact tested environments, supported features, and known degradation. Validate denied and revoked permissions, races, reloads, crash windows, and public-server abuse before the builder release. |

## 4. Authority and lifecycle

The client renders and requests. A provider can propose a design or explain a task. The server resolves the actor, owns the plan and revision, checks approval and capabilities, and performs bounded actions. Store job, custody, and approval state on the server, linked to the companion identity. Keep client code out of dedicated-server class loading. Never store job or inventory authority on the transient entity or in provider output.

A job follows draft → reviewed preview → approved → queued/running → completed, cancelled, or waiting with a cause. Waiting can reflect missing supplies, manual work, logout/dismissal, stale approval, protection, AI, or reconciliation. Resume rechecks each relevant gate and carries forward verified completed steps. A build step becomes eligible when its prerequisites are verified, approval covers the current action, the companion can reach it, and the required items and ancillary inputs are ready. A job completes only when all required steps and manual placements are verified. Functional commissioning remains a distinct result.

**Partial-supply example.** A house has wall sections and a roof supported by those walls. With only enough held blocks for one safe wall section, build that section, record what was used, and expose the remaining shortage. Do not start roof steps lacking support. Gather or craft within the approved budget where permitted, or ask for supplies. An unsupported door remains an explicit manual step even after handoff. A player placing the correct door can satisfy the manual step after server verification. A player changing an approved wall location unexpectedly pauses dependent work.

## 5. Decisions to close before their implementation gates

| Decision | Proposed starting point and required evidence |
| --- | --- |
| D1 Movement, safety and position | For M2, use owner-only same-dimension locomotion in loaded terrain and a stay state on older records. Preserve explicit M1 recall semantics. Do not enable autonomous teleport until safe landing, protection behavior, and bounded attempts are specified. Test a move across a chunk boundary followed by real unload and restart. |
| D2 Custody and offline fairness | Compare a durable transfer journal with narrower, verifiable transactions against real inventory and save boundaries. Define which interrupted operations can be retried, staff reconciliation authority, and offline reservation release. Avoid automatic transfer replay and never release stock already moved or consumed. |
| D3 Approval and partial supply | Define approval roles and revision/site evidence. Adopt per-step readiness for tools, fuel, scaffolding, and supports as the proposed default. Choose how manual placement is verified and how approvals respond to player work and adapter/protection changes. Review the incremental policy with adversarial examples. |
| D4 Protection and discovery | Establish the real actor/permission and revocation contracts against pinned FTB/NeoForge versions. Establish trustworthy natural-source evidence in existing and new worlds. Keep unproven worlds/resources locked for simulated gathering. |
| D5 Provider and privacy | Verify the official BharatCode route from a client, choose local credential storage, and define request expiry, retry/spend limits, retention, and alternative-provider verification. A deterministic mock can test the server boundary before live access. |
| D6 Production and engineering | Select the first adapter from actual ATM10 availability and supported APIs. Set observable commissioning criteria, external machine reconciliation, safe effect bounds, and measured query/tick limits before claiming the capability. |
| D7 Release and data lifetime | Decide release versioning, schema upgrade and downgrade rules, support export redaction, and disable/uninstall behavior with confirmed items in custody. Publish no supported profile without its own evidence. |
