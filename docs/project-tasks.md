# BharatCode Companion project task list

**Goal** — Close the client evidence gap on the corrected M1 jar, then build a small protected construction loop that can grow into the full builder, production, and engineering releases.

**Architecture** — Keep the companion identity and execution authoritative on the server. Keep AI credentials on the owner's client and route all new proposals through the same server validation and approval flow. [Project specification](project-spec.md)

**Baseline** — Java 21, Minecraft 1.21.1, NeoForge 21.1.265, Gradle 8.14.2, ModDevGradle 2.0.91, and ATM10 8.5. Keep the pinned clean NeoForge and ATM10 environments distinct in the test record.

Task IDs are stable. **P0** is the immediate gate, **P1** is the next implementation, **P2** completes the first builder release, and **P3** covers production and engineering. Check a task off when its evidence is recorded against a specific build. M1–M5 keep the numbering from the original baseline. The builder slice is an internal milestone, with settlements still in the first builder release.

Record any client/server errors and check that the environment was left unedited by the companion.
- [ ] **M1-02 · Real remote recall, unload and JVM restart.** Depends on M1-01. In a disposable world with prepared terrain, record the companion UUID and dimension. Repeat with remote dismiss, then summon while the old area is unloaded. Verify ACTIVE cross-dimension refusal and DORMANT resummon in the new dimension. Stop and restart the JVM once with ACTIVE authority and once with DORMANT authority. Trigger documented restoration near the recorded chunk or with the charm, and verify one or zero projections as appropriate and the same UUID after resummon. Separately exercise readable bad data in a copied fixture and confirm fail-closed behavior and preservation. Record warm/generated terrain versus cold terrain for any timeout.
- [ ] **M1-03 · Pinned ATM10 smoke.** Depends on M1-01 and M1-02. Repeat the core M1 checks on a matched ATM10 8.5 client/server profile using the same jar hash. Cover render/craft, two-player identity, one-use remote recall, dismiss/resummon, and restart. Record the exact pack, loader, mod list, hashes, and differences from clean NeoForge. - [ ] **DEV-01 · Establish a reviewable source baseline.** Before M2 edits, locate or establish the project's canonical Git repository and baseline the verified source, wrapper, resources, and planning docs. This workspace currently lacks Git metadata. Exclude build products, development worlds, runtime logs, and local credentials. ## P1 · M2–M5 foundations

### M2 · Movement, with zero block or inventory mutations

- [ ] **M2-01 · Owner commands and movement state.** Depends on M1-04 and DEV-01. Settle D1. Start with owner-only follow, stay, set-home, and return-home through a minimal server-side command surface. Keep mode and home separate from active/dormant and last position. Load schema-v2 worlds with a safe default. Reject non-owner, offline, fake, spectator, wrong-dimension, and stale requests as applicable. Check save/load, rejected inputs, and unchanged charm behavior.
- [ ] **M2-02 · Bounded same-dimension navigation.** Depends on M2-01. Enable only necessary navigation in `CompanionEntity.java` and connect it to authority in `CompanionService.java`. Stop at an unloaded, unsafe, inaccessible, or repeatedly unreachable route. Cancel stale navigation on recall, dismiss, owner logout, spectator transition, and dimension change. Keep explicit charm recall on the tested lifecycle path. Verify open path, obstruction, safe stop, no autonomous chunk loading, and no owner overlap.
- [ ] **M2-03 · Position and restoration while moving.** Depends on M2-02. Define how `CompanionRecord.java` and `CompanionSavedData.java` checkpoint the latest safe position across chunk transitions, unload, and graceful stop without saving an entity snapshot or writing every tick. Add targeted cases to `CompanionLifecycleGameTests.java` for a moved companion that unloads or is recalled while hidden. Replay movement across a chunk boundary and a real stop/restart. Close M2 when UUID/name survive, old areas hold no stale copies, no extra chunk tickets remain, and logout/dismissal cannot leave an active movement goal.

### M3 · Material custody and reservations

- [ ] **M3-01 · Storage and transfer contract.** Depends on M2-03. Resolve D2 with a representative save/interruption experiment. Define persisted schemas, item identities/components, paged access, bounded processing, and location/custody states. Produce a table of failure windows and what can be proven after restart. Old or future data must preserve holdings or fail closed.
- [ ] **M3-02 · Held inventory, reservation, and recovery.** Depends on M3-01. Implement real held-item accounting and reserve/release/consume transitions. Keep external transfer disabled until M4. Verify competing reservations, component-distinct stacks, crash before/after debit or credit, uncertain transfer quarantine, storage exhaustion, cancellation, and offline release. A reservation can never be consumed without held stock.
- [ ] **M3-03 · Visible custody and reconciliation.** Depends on M3-02. Expose read-only counts, disputed transfers, provenance/correlation IDs, and staff-assisted recovery. Validate repeat recovery, bounded page access, and redacted exports. Connect legitimate player handoff, sorting and delivery after M4-02.

### M4 · Protection before world changes

- [ ] **M4-01 · Protection contract and pinned API proof.** Depends on M2-03 and may be investigated while M3 is in progress. Resolve the protection half of D4. Probe clean NeoForge and ATM10's actual FTB Chunks/Teams build. Define allow/deny/unknown for build, break, interact and transfer, actor identity, work zones, and revocation. An unknown integration stays disabled for those actions.
- [ ] **M4-02 · Enforced mutation gateway.** Depends on M4-01 and M3-02 for transfers. Route world and external inventory changes through one server-side permission boundary. Check each action immediately before mutation. Verify allowed/denied/unknown outcomes, other-player and server-team claims, container trust, revocation after approval, and chunk or world changes between preview and execution. Unknown protection still permits approved internal held-stock crafting under normal lifecycle rules.
- [ ] **M4-03 · First protected placement.** Depends on M4-02. In a test-only or gated internal build, place one supported block from held stock through the production action boundary. Verify claim denial does zero edits and debits, placement rejection preserves stock, and an interrupted placement can be reconciled against world state without a duplicate placement or debit. This is the gate for all builder mutations.

### M5 · Addressed chat and client AI proposals

- [ ] **M5-01 · Deterministic commands and proposal boundary.** Depends on M2-01. Resolve the request/validation part of D5. Implement addressed chat and predefined command routing. With a local mock, validate server-issued request identity, expiry, actor, revision, action schema, and caps. A valid response can create a draft only. Verify spoofed, replayed, stale, oversized, and malformed responses are rejected and unrelated chat is excluded.
- [ ] **M5-02 · Verified BharatCode client route.** Depends on M5-01. Prove the official client route and credential storage before enabling calls. Implement disclosure, scoped context, cancellation, expiry, cost/rate limits, and safe provider failure. Test that server payloads, logs, and support exports omit the key. Explicitly configured alternatives use the same verification and consent boundary.
- [ ] **M5-03 · Trusted players and memory.** Depends on M5-02. Define trusted order scopes and owner consent for allowance use, including revoke and expiry. Persist named places, preferences and authorized memory, with a local forget control. Verify trusted players cannot self-authorize spending or approvals, logout cancels provider work, and an expired response cannot resume a job. Coordinate approval roles with B-01.

## Running the gates

Use the project JDK 21 and Gradle wrapper. For code changes, run `./gradlew build` and `./gradlew runGameTestServer`, and retain the independent evidence each manual or pack gate needs. A development GameTest run proves the engine behavior it exercises. Client controls, full restarts, dedicated multiplayer, and a particular pack each need their corresponding test environment. Use disposable worlds and keep the corrected M1 artifact available for comparison.

The five highest-risk cases to preserve as the project grows are a hidden moved projection after unload (M2-03), an uncertain debit across a save boundary (M3-01/02), permission revoked immediately before an edit (M4-02), a valid but stale/replayed AI response (M5-01), and partial supplies with manual placement plus a changed site (B-01/02). Link the resulting evidence to these IDs before advancing the relevant release gate.
